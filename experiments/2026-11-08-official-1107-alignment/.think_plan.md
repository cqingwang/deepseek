# 官方 1107 对齐与 ten-boot 验证计划

## 目标

- 以官方 `offical/main` 的正式 1107 基线为对照，复现官方镜像身份和运行参数。
- decode 达标或超越官方 README 标称：c1 `82.623 tok/s`、c8 `207.447 tok/s`、
  c16 `272.863 tok/s`；同时测量 c2/c4，且 c1-c4 不得低于本站官方 1107 基线超过约 3%。
- prefill 主排名仍用 cold source-text `8K/16K/32K/64K/128K/256K` 六档 tok/s
  的算术平均，取十次有效部署中的最高值。
- prefill 大档不得低于本站官方 1107 基线：`32K/131K/262K/524K/1M`。
- 运行参数优先；只有运行参数无法达到目标时才做镜像内源码/二进制改动。

## 验收门禁

1. 身份门：四机镜像 tag、full image ID、六棵 source tree label 一致；实际启动
   argv/env/mount/拓扑与已落盘方案逐项一致。
2. decode 门：c1/c8/c16 达到官方 README 标称；c1-c4 相对官方 1107 基线不出现
   超过 3% 的稳定回退。
3. prefill 主门：六档 cold source-text 均值高于官方 1107 本地基线，且以十次
   部署中的最高均值为最终选择。
4. prefill 大档门：32K/131K/262K/524K/1M 相对官方 1107 本地基线不下降超过
   测量噪声容差。
5. 稳定门：四机 `OOMKilled=false`、restart 0、memguard active、failed units 0、
   `/v1/models=200`、无 Xid/NVRM/OOM/fault。
6. 质量门：记录官方 1107 的 release quality delta；不把其已知
   greedy/perplexity 变化与性能回归混为一谈。

## 十次部署阶梯

| 部署 | 目的 | 变量 |
| ---: | --- | --- |
| 01 | 官方基线 | 1107 recipe 原值：batch/threshold `16384/16288`，all-gather `2 MiB`，CUDA connections `32`，NCCL channels `4` |
| 02 | 当前已证参数迁移 | batch/threshold `65520/65424`，all-gather `8 MiB`，channels `8`，CUDA connections `64`，QPS `2` |
| 03 | 大 chunk 中值 | batch/threshold `49152/49056`，其余沿用 02 |
| 04 | batch 上限复核 | `65535/65439`，其余沿用 02 |
| 05 | all-gather 单键 | 02 的 batch 面 + all-gather `4 MiB` |
| 06 | channels 单键 | 02 的 batch 面 + NCCL channels `4` |
| 07 | QPS 单键 | 02 的 batch 面 + QPS `1` |
| 08 | threshold 分离 | 02 的 batch + threshold `32768` |
| 09 | 最佳组合复核 | 前八次中六档均值最高且 decode 合格的参数 |
| 10 | clean-boot 收尾 | 与 09 相同，先完整 stop、确认四机无 target 容器后启动 |

若某次启动失败，保留原始错误并计入十次上限；同一失败最多重试两次。任何有收益的
参数组合必须在该次部署后立刻写入 `scores.json` 和对应 `runs/run-NN/`。最终只保留
十次中门禁全部通过且六档均值最高的一次运行态。

## 测量协议

- prefill 六档：本地 `servebench prefill`，source-text，尺寸
  `8192,16384,32768,65536,131072,262144`，每档 2 次，取均值；记录每档样本。
- prefill 大档：官方 `servebench prefill`，尺寸
  `32768,131072,262144,524288,1000000`；官方基线复核至少 1 次，候选只在六档胜出后
  跑完整大档以减少无效时间。
- decode：c1/c2/c3/c4 使用既有 30 秒三批协议，c8/c16 使用官方 60 秒 warmup +
  300 秒 closed-loop 协议；任何 decode 门失败都拒绝该 prefill 方案。
- 每次候选只改变一个主要运行变量；组合候选必须明确列出继承基线和全部变化。

## 收尾结果

- 用户在 run-06 后要求直接使用最佳方案收尾；最终用 run-07 clean profile
  清除三个无消费者的旧 binary-prefill env，并重新确认六档均值
  `7,875.85 tok/s`，相对本地官方 1107 基线 `+6.08%`。
- 最终运行参数为 `--max-num-batched-tokens 65520`、
  `--long-prefill-token-threshold 65424`、all-gather 8 MiB、
  NCCL channels 8、CUDA connections 64、NCCL QPS 2；三个旧
  binary-prefill 容器 env 显式置 null。
- 官方 decode 长测 c1/c8/c16 为 `77.66 / 194.62 / 242.25 tok/s`，
  README 目标未达到；负载中 GPU 2184–2190 MHz、无 throttle，运行参数
  路径到此为止，下一阶段转镜像 binary/build provenance。
- 环网审计发现 spark-a/spark-c 的运行时对角 `/32` 路由曾在链路重载后
  丢失；停机后执行既有 `mesh-up.sh` 恢复。相同参数对照仅 `+0.43%`，
  但后续部署前仍必须检查 route/TC/marker。
- 最终证据冻结在 `frozen-best/`；Docker Build Cache、远端 `.work`、
  本地 official clone/image tar、临时日志和冗余 ring probe 二进制已清理。
  保留当前镜像、1030、image03、模型、`/cache` 与共享环网。
- 父级回归 `69 passed`；frozen `SHA256SUMS`、`git diff --check`、
  shell 语法和 JSON 解析通过。
